## 1. Что это за приложение

Личное Android-приложение (в перспективе — и iOS, без переписывания архитектуры) для одного пользователя. Автоматизирует два процесса:

1. Занесение данных с бумажных чеков (Date, Subtotal, GST) в Excel-отчёт о расходах (Mileage Report, лист «Truman Homes») через офлайн-распознавание фото чека.
2. Ведение табеля рабочего времени (Timesheet) — шаблонное заполнение рабочего дня с ручным редактированием.

Интернет на телефоне в целом доступен и это нормально (нужен и для отправки файлов). Принципиально другое: сам процесс распознавания чека должен всегда идти локально на устройстве, а не через удалённый сервис — телефон не должен отправлять фото чека или его данные никуда наружу для обработки. Никаких API-ключей, никаких облачных OCR-сервисов, никакой аналитики и рекламы.

Название приложения — **ExpenseFlow**: используй его и как имя Flutter-проекта (в подходящем формате, например `expenseflow`), и как отображаемое название под иконкой на телефоне. Название не переводится — остаётся «ExpenseFlow» одинаково и в английской, и в русской версии интерфейса.

**Термины, которые используются по всему документу как есть, без перевода и без расшифровки далее:** GST = Goods and Services Tax, федеральный налог с продаж в Канаде (в этом документе — синоним «налог», «Tax»); STAT = statutory holiday, законный оплачиваемый праздничный день в Канаде/Альберте (Victoria Day, Canada Day и т.п. — конкретный список уже есть в `payroll_periods_seed.json`, см. раздел 4).

## 2. Технологический стек

- **Flutter (Dart)** — кроссплатформенность (Android сейчас, iOS позже) и сборка через Android Studio. Минимальная поддерживаемая версия Android — конкретных требований нет, выбери сам разумный современный порог (нет старого устройства, под которое нужно специально подстраиваться).
- **Excel:** пакет `excel` (чистый Dart, открытый исходный код, pub.dev). Используем именно его, а НЕ `syncfusion_flutter_xlsio`. Причина: Syncfusion — платный продукт с бесплатной Community-лицензией только для отдельных разработчиков/малого бизнеса (выручка < $1 млн США, < 5 разработчиков в организации). Если это приложение позже возьмёт «на баланс» компания, в лицензии могут возникнуть вопросы. `excel` бесплатен всегда и для всех, без каких-либо условий. Для тонких операций (раздел 7) не полагайся на «магию» библиотеки — пиши точные, явные операции по уже зафиксированной структуре шаблона (раздел 4).
- **OCR:** `google_mlkit_text_recognition` — распознавание текста локально на устройстве встроенной моделью ML Kit, без API-ключей и без отправки фото или данных чека на удалённый сервис для обработки. Если сама модель ML Kit при первом запуске подгружается через Google Play Services — это не проблема, интернет на телефоне есть; важно только то, что распознавание текста всегда идёт локально, а не через облачный API (не Cloud Vision API и не аналогичные платные/облачные сервисы).
- **Камера/галерея:** `image_picker` — источник камера ИЛИ галерея, пользователь выбирает каждый раз.
- **Поделиться файлом:** нативный Share Intent Android (`share_plus` или аналог) — НЕ прямая интеграция с API email/Teams/WhatsApp/Telegram. Показываем стандартное системное меню «Поделиться», которое само выводит список всех подходящих приложений, установленных у пользователя.
- **Локальное хранилище:** `path_provider` + Storage Access Framework для явного экспорта в память телефона.
- **Настройки:** `shared_preferences`.
- **Локализация:** встроенный Flutter i18n, языки — English (по умолчанию) и Русский.
- **Разбор чисел, введённых вручную:** независимо от языка интерфейса, любое поле ручного ввода числа (Subtotal, GST в разделе 8; KM в разделе 9; ставка $/км в разделе 11) должно одинаково принимать и точку, и запятую как разделитель дробной части («5.29» и «5,29» — одно и то же число) и конвертировать в нормальный числовой тип (Dart `double`) до того, как что-либо уйдёт на запись в Excel. В самом файле Excel это никак не проявляется: числа в формате OOXML всегда хранятся с точкой независимо от локали (проверено напрямую в XML файла — `<v>0.56</v>`, не `0,56`) — запятая-разделитель существует только на экране приложения, в момент, когда человек печатает число, а не в файле.

## 5. Жизненный цикл периода

- При первом запуске приложение копирует данные из `payroll_periods_seed.json` в собственное перезаписываемое локальное хранилище (файл/база в директории приложения, НЕ bundled-ассет — ассет доступен только на чтение и не может расти). Дальше приложение всегда читает и дополняет именно эту локальную копию, а не ассет напрямую — так пользователь сможет сам добавлять новые периоды (см. ниже), когда встроенный список закончится.
- При запуске приложение сравнивает сегодняшнюю дату со списком периодов (локальная копия) и определяет текущий период (start ≤ сегодня ≤ end).
- Если для текущего периода ещё нет созданных файлов — создать оба автоматически, без участия пользователя:
  - Скопировать `Truman_Homes_Mileage_Report_TEMPLATE.xlsx` → заполнить M3 (подпись периода), B3 (имя из Настроек) → инициализировать строку 8 как строку Kilometers (раздел 7).
  - Скопировать `Truman_Homes_Timesheet_TEMPLATE.xlsx` → заполнить C2/C5/C6 → автозаполнить рабочие дни (раздел 10).

  **Автосоздание работает ТОЛЬКО для текущего периода — ни для архивных, ни для будущих.** Это важно из-за срока хранения (раздел 11): он удаляет файлы старых периодов, но сам период остаётся в локальном списке (список — календарные данные, файлы — работа). Если открыть такой архивный период и применить общее правило «файлов нет → создать из шаблона», пользователь увидит пустой отчёт на месте давно сданного и вполне может принять его за настоящий. Правильное поведение: для архивного периода без файлов показать пояснение («файлы этого периода удалены согласно сроку хранения»), для будущего периода, добавленного заранее, — «период ещё не начался», и в обоих случаях ничего не создавать.
- Именование файлов: `MileageReport_<periodStart>_<periodEnd>.xlsx` и `Timesheet_<periodStart>_<periodEnd>.xlsx` (даты в формате ГГГГ-ММ-ДД), чтобы сортировались по имени хронологически.
- Файлы прошлых периодов хранятся согласно настройке «Хранение» (раздел 11) и доступны из простого списка периодов в приложении — прошлый период можно открыть и отредактировать теми же экранами, что и текущий (см. также раздел 14).

**Когда периоды заканчиваются** (в исходных данных список кончается 23 января 2027, но логика ниже реагирует на то, что периодов осталось мало, а не на конкретную дату — значит будет работать точно так же и в любой следующий раз, когда список опять понадобится продлевать):
- Когда после текущего периода в списке остаётся 2 периода или меньше — один раз показать напоминание (тем же механизмом, что и в блоке про напоминания ниже) с предложением заранее добавить следующие периоды, не дожидаясь, пока список закончится по-настоящему.
- Форма добавления периода (в Настройках) — по полям:
  - **Период (start/end)** — предзаполнены автоматически, продолжая тот же шаблон, что и в остальном списке; поля остаются редактируемыми на случай, если работодатель когда-нибудь изменит саму схему периодов. Шаблон точно такой (проверено по всем 21 периоду в `payroll_periods_seed.json`, исключений нет): периоды чередуются — **9–23 числа того же месяца**, затем **24 число – 8 число СЛЕДУЮЩЕГО месяца** (например, 24 марта – 8 апреля; 24 декабря – 8 января). Обратите внимание: второй период НЕ заканчивается в конце месяца, он переходит через границу месяца на 8 число следующего. Начало нового периода — всегда следующий день после конца предыдущего, без разрывов.
  - **Срок сдачи (due)** — date picker для даты + время. Дата предзаполнена датой конца периода (`end`) — так в 19 периодах из 21; в двух исключениях `end` попадал на воскресенье, и работодатель переносил срок на предшествующую пятницу, поэтому если предзаполненная дата попала на выходной, стоит перепроверить её по документу от работодателя особенно внимательно. Время предзаполнено 4:30 PM (во всех 21 периоде время сдачи всегда 16:30 — надёжный, устойчивый паттерн). Оба поля редактируются: пользователь меняет дату, если работодатель назвал другую, а время трогает, только если оно отличается от обычного.
  - **Отдельный срок для рабочих выходных (weekend_alt_due)** — переключатель «есть отдельный срок для рабочих выходных», выключен по умолчанию (у большинства периодов его нет). Если включить — появляется второй date+time picker, по умолчанию предзаполненный 8:30 AM (тот же устойчивый паттерн, что и у due).
  - **STAT-праздники (stat_holidays)** — список, изначально пустой; кнопка «+ Добавить праздник» добавляет строку: текстовое поле для названия (например «Family Day») + date picker для даты. Можно добавить сколько угодно строк (максимум в исходных данных — 2, Christmas Day и New Year's Day в одном периоде) или не добавлять ни одной; лишнюю строку можно удалить.
  - **Ставка $/км (km_rate)** — число, предзаполнено текущим значением из Настроек (раздел 11) на момент открытия формы; редактируется, если работодатель именно для этого периода назвал другую ставку.
  - Лёгкая валидация перед сохранением: end позже start, due и даты STAT-праздников попадают в диапазон start–end, и (сверх этого) новый период не пересекается ни с одним уже существующим периодом в списке — пересечение блокирует сохранение с понятным сообщением (скорее всего, опечатка в дате). Разрыв между периодами (без пересечения) не блокируется — это может быть осознанным, если периоды добавляют не по порядку.
  - «Сохранить» — период дописывается в локальный список (см. выше) и сразу становится доступен приложению; уже добавленный вручную период можно потом снова открыть в этой же форме и поправить, как обычный редактируемый список.
- Период, добавленный вручную, дальше ничем не отличается от периода из исходного `payroll_periods_seed.json` — он в том же локальном списке, поэтому вся остальная логика (генерация файлов выше, авто-STAT в разделе 10, напоминания ниже) применяется к нему одинаково, без особых случаев.
- Если пользователь всё же дотянул до даты за пределами последнего известного периода, не добавив новый заранее, — показать блокирующее (для входа в текущий период) сообщение с той же формой добавления периода.

**Напоминания о сдаче:** у каждого периода уже есть точный срок сдачи (`due` в списке периодов) — датасет для этого собирать не нужно, он уже есть. При создании/обнаружении периода планировать одно локальное уведомление на `due − 2 дня`. Технически недорого: пакет `flutter_local_notifications` (зрелый, полностью офлайн, без сервера и без API-ключей). Точность до минуты не нужна — подойдёт «неточный» (inexact) будильник, а значит не требуется более чувствительное разрешение Android на точные будильники — только обычное разрешение на показ уведомлений (на Android 13+ система спросит один раз, как в любом другом приложении). По тапу на уведомление — открывать приложение сразу на экране отправки (раздел 12) этого периода, чтобы напоминание сразу вело к действию. Использовать основной `due`, а не `weekend_alt_due` — это отдельный редкий случай для рабочих выходных, не должен усложнять обычный сценарий напоминания.

| A | Date | приложение (дата с чека, либо дата для строки Kilometers) |
| B | Description | «Kilometers (N)», где N — реальное посчитанное число (например «Kilometers (142)»), не буква «N» — для строки км приложение вычисляет и вписывает его само, полностью автоматически (раздел 7); для чеков — необязательный текст, который пользователь вписывает вручную на экране подтверждения (см. раздел 8) |
| C | Office | не используется, всегда пусто |
| D | Materials | приложение (Subtotal с чека) |
| E | Travel | пользователь вручную в самом Excel; ИСКЛЮЧЕНИЕ — строка Kilometers: там приложение само вычисляет и записывает `N × rate`, где `rate` — по правилу старшинства раздела 6.2 (на практике всегда `G1`), полностью автоматически (раздел 7) |
| F | Phone | не используется, всегда пусто |
| G | Meals | не используется, всегда пусто |
| H | Showhome | не используется, всегда пусто |
| I | Net before GST | ФОРМУЛА, не трогать: `=+H{r}+G{r}+F{r}+E{r}+D{r}+C{r}` |
| K | GST | приложение (GST с чека) |
| L | TOTAL | ФОРМУЛА, не трогать: `=+K{r}+I{r}` |

Строка 28 (Subtotals) и ячейка M30 (TOTAL CLAIMED) — формулы, не трогать. Ячейка I28 намеренно оставлена как есть (в оригинале — захардкоженный 0, а не формула СУММ, как у соседей) — не исправлять, так решил пользователь.

### 6.2 Mileage Report → лист «Driving Details»

Область данных: строки 2–18 (17 строк на период).

| Колонка | Назначение |
|---|---|
| A | Date |
| B | Trip — свободный текст, вводит пользователь, без автодополнения |
| C | KM — число, десятичные значения разрешены |
| D | ФОРМУЛА, не трогать: `=SUM(C{r}*$G$1)` |

Строка 19 (Total) — формулы `=SUM(C2:C18)` и `=SUM(D2:D18)`, не трогать.

`F1` = подпись «Rate ($/km):» (не трогать), `G1` = сама ставка — число, не формула, приложение пишет туда `period.km_rate` при создании периода и при каждом изменении ставки для текущего периода (раздел 11), так же, как в любую другую ячейку-значение. Формула в D теперь ссылается на `$G$1`, а не на захардкоженное число, поэтому при открытии файла в самом Excel «Total $» на этом листе и Travel на «Truman Homes» всегда считаются по одной и той же ставке — они больше не могут разойтись.

**Приоритет источников ставки (важно — значение ставки хранится в трёх местах).** Умолчание в Настройках, `period.km_rate` у периода и `G1` в файле — у каждой копии своя роль, поэтому ни одну нельзя убрать; вместо этого действует жёсткое правило старшинства:
- **Файл периода ещё не создан** → берём `period.km_rate`; если у периода нет этого поля (старый период, см. раздел 4) → умолчание из Настроек.
- **Файл создан** → авторитетен `G1` из файла: и Travel в строке Kilometers, и любой пересчёт читают ставку оттуда, а не из Настроек и не из `period.km_rate`.
- **Смена ставки** (раздел 11) пишет `G1` и `period.km_rate` вместе, одной операцией — никогда только одно из двух, иначе они разойдутся молча.
- Тест на согласованность — раздел 13, п. 11.

Реализуй ввод времени через time picker (не свободный текст), чтобы результат всегда был корректно отформатирован и Hours считался однозначно: `Hours = (Finish − Start) − Lunch − Coffee`, в часах.

## 7. Логика строки «Kilometers» — реализовать точно

Правила:
- Строка Kilometers всегда стоит с ровно одной пустой строкой-отступом после последнего чека; если чеков ещё нет — она первая строка данных, без отступа.
- Дата в этой строке = всегда последний день текущего периода (`period.end`), а не сегодняшняя дата и не дата последнего чека.
- Description = всегда `Kilometers (N)`, где N — не буква, а реальное число: сумма всех значений KM с листа Driving Details за текущий период, которую приложение считает и подставляет само, без участия пользователя (например, если в Driving Details в сумме набежало 142 км — в ячейку идёт текст «Kilometers (142)»); если Driving Details пуст — N = 0, то есть «Kilometers (0)».
- Колонка Travel (E) для этой строки вычисляется приложением автоматически: `N × rate`, округлённое до 2 знаков после запятой, где N — та же сумма KM, что и в Description, а `rate` берётся по правилу старшинства из раздела 6.2 («Приоритет источников ставки») — то есть на этом этапе всегда из `G1` листа Driving Details, потому что файл периода к моменту расчёта Travel уже существует. Пересчитывается каждый раз вместе с Description — и при добавлении чека, и при любом изменении в Driving Details. Касается только строки Kilometers: Travel у обычных строк-чеков остаётся пустым и полностью ручным, как и раньше.
- При добавлении нового чека строка Kilometers не пересоздаётся, а сдвигается (вместе с пустой строкой-отступом) на одну позицию вниз; новый чек занимает освободившееся место.
- При любом изменении в Driving Details Description и Travel в строке Kilometers пересчитываются автоматически, без движения строки.

**Инициализация нового периода** — сразу после создания файла периода (раздел 5), до первого чека, в таком порядке: сначала на листе Driving Details записать `G1 = period.km_rate` (раздел 6.2 — с этого момента `G1` становится авторитетным источником ставки для этого файла, и формула колонки D сразу считает по правильной ставке), затем в строку 8 листа Truman Homes: `A8 = period.end`, `B8 = "Kilometers (0)"`, `E8 = 0` (0 × ставку = 0 при любой ставке; C, D, F, G, H, K — пусто). Порядок важен: если записать строку 8 раньше `G1`, расчёт Travel попытается прочитать ставку из ещё пустой ячейки.

**Алгоритм при сохранении нового чека:**

```
km_row = строка, где в колонке B текст начинается на "Kilometers ("

ЕСЛИ km_row == 8:                      # чеков ещё не было, отступа нет
    new_km_row = 10
    перенести строку km_row в new_km_row: A не меняется (по-прежнему period.end),
        B пересчитать как "Kilometers (N)" с текущей суммой KM,
        E пересчитать как round(N × rate, 2), где rate = G1 с листа Driving Details (раздел 6.2)
    убедиться, что строка 9 пуста — это новый отступ
    записать новый чек в строку 8 (A=Date, B=Description если указан, D=Subtotal, K=GST)

ИНАЧЕ:
    gap_row = km_row - 1
    new_km_row = km_row + 1
    ЕСЛИ new_km_row > 27:
        показать предупреждение "строки закончились — дальше редактируйте файл прямо в Excel"
        ЗАВЕРШИТЬ операцию здесь: ничего не писать и не двигать, ни одна из строк ниже не выполняется
    ИНАЧЕ (new_km_row ≤ 27):
        перенести строку km_row в new_km_row: A не меняется (по-прежнему period.end),
            B пересчитать как "Kilometers (N)",
            E пересчитать как round(N × rate, 2), где rate = G1 с листа Driving Details (раздел 6.2)
        очистить старую строку km_row — она станет новым отступом
        записать новый чек в строку gap_row (A=Date, B=Description если указан, D=Subtotal, K=GST)
```

Колонки I и L (формулы) уже присутствуют в каждой строке 8–27 шаблона — при переносе/очистке их не трогать, они продолжат работать для новой позиции автоматически.

**Алгоритм при изменении Driving Details:**

```
km_row = строка, где в колонке B текст начинается на "Kilometers ("
N = сумма всех значений колонки C на листе Driving Details за период
записать B(km_row) = "Kilometers (" + N + ")"
записать E(km_row) = round(N × rate, 2), где rate = G1 с листа Driving Details (раздел 6.2)
```
Строка не двигается, дата не меняется.

**Технический момент для устойчивости:** не переписывать Excel-файл на каждое нажатие клавиши в поле KM — пересчёт и запись должны происходить один раз, при сохранении/потере фокуса поля, а не на каждое изменение текста. Также на каждом шаге обоих алгоритмов этого раздела заново искать `km_row` по фактическому содержимому файла (как и написано в псевдокоде выше), а не полагаться на запомненную с прошлого раза позицию — тогда последовательность операций можно спокойно прервать на середине и продолжить позже, не потеряв согласованность структуры листа.

## 8. Экран добавления чека (сканирование или полностью ручной ввод)

1. Пользователь выбирает способ добавления — три равноправных варианта в одном месте интерфейса: **камера**, **фото из галереи**, **ввести вручную** (без фото и без OCR вообще).

**Камера / галерея:**

2. `google_mlkit_text_recognition` извлекает текст с фото. Само фото нигде не сохраняется — используется только в оперативной памяти на время обработки, после распознавания удаляется.
3. Парсер ищет:
   - **Дату** — пробовать несколько форматов (ДД/ММ/ГГ, ДД/ММ/ГГГГ, М/Д/ГГГГ, текстовые месяцы). Когда день ≤ 12 и обе интерпретации (ДД/ММ и ММ/ДД) календарно валидны — не сдаваться сразу, а снять неоднозначность через контекст: Mileage Report сдаётся раз в 2 недели, и чек почти всегда сканируют вскоре после покупки, поэтому дата покупки практически никогда не бывает в будущем и почти никогда не старше ~месяца от сегодняшнего дня. Порядок:
     1. Посчитать обе интерпретации.
     2. Отбросить те, что в будущем относительно сегодняшней даты устройства (чек не может быть «из будущего»).
     3. Если среди оставшихся ровно одна попадает в окно «сегодня минус 35 дней — сегодня» (35 — разумное значение по умолчанию с запасом на «месяц плюс пара дней»; можно потом подстроить) — использовать её как результат распознавания (пользователь по-прежнему видит и может поправить её на экране подтверждения, как любое другое поле).
     4. Если и после этого остаётся больше одного правдоподобного варианта (оба в окне или оба вне его) — оставить поле пустым, как раньше, пусть пользователь впишет сам.
   Это сужает случаи, когда дата остаётся пустой, но не отменяет общее правило «при реальной неоднозначности — не гадать».
   - **Subtotal** — строка с «Subtotal»/«SUBTOTAL».
   - **Налог** — любой из синонимов «GST», «GST/HST», «HST», «Sales Tax», «Tax» — всё это одно и то же поле GST.
   - Поиск обеих меток — без учёта регистра букв, по вхождению слова в строку распознанного текста (не обязательно вся строка целиком должна совпадать с меткой); число, которое идёт рядом с найденной меткой на той же строке, — и есть искомое значение.
   - Что не найдено — остаётся пустым, не блокирует переход к следующему экрану.

**Ввести вручную:**

4. Экран камеры/галереи и OCR полностью пропускаются. Сразу открывается экран подтверждения (см. ниже), но поля Date/Subtotal/GST начинаются пустыми и сразу доступны для ввода — распознавать нечего, поэтому кнопка «Редактировать» здесь не нужна и не показывается, есть только «Сохранить». Date вводится через обычный date picker — никакого разбора текста и связанной с ним неоднозначности форматов здесь нет и быть не может, пользователь просто выбирает день в календаре. Если выбранная дата выходит за пределы текущего открытого периода (start–end) — мягкое, не блокирующее предупреждение при сохранении (в духе проверки GST ≈ 5%, ниже): дата может быть верной (например, чек за пару дней до начала периода), поэтому не запрещаем, только обращаем внимание.

**Экран подтверждения (общий для всех трёх способов):**

5. Показывает 4 поля: Date, Subtotal, GST, Description.
   - Description — это список купленных товаров, например «Home Depot - toilet fill valve, garbage bags, lysol, bulbs» или «Rona - filters, door handles, silicone» (магазин, затем через запятую позиции — по тому же принципу, что и в исходных примерах файла). Поле принципиально не пытается ничего распознавать и не подсказывает формат никакими намёками/плейсхолдерами — простое пустое текстовое поле без какой-либо подсказки, которое от начала до конца заполняет только человек, во всех трёх способах добавления без исключений. Необязательно — можно оставить пустым.
   - Если Subtotal и GST оба заполнены, Subtotal не равен нулю, и GST заметно отличается от 5% Subtotal (например, `|GST − 0.05×Subtotal| / |0.05×Subtotal|` больше ~15%, по модулю — чтобы корректно работало и на отрицательных суммах, например при чеке-возврате) — мягкое, не блокирующее предупреждение рядом с полем GST. Если Subtotal = 0 — проверку просто пропустить (не на что делить, не показывать предупреждение, не пытаться вычислить процент). Действует одинаково для OCR и для ручного ввода.
6. Кнопки: после камеры/галереи — **Редактировать** (Date/Subtotal/GST становятся обычными полями ввода вместо распознанного значения) и **Сохранить**; после «Ввести вручную» — только **Сохранить** (редактировать нечего, всё и так вводится вручную). Description в любом случае всегда сразу доступно для ввода, кнопке «Редактировать» не подчиняется.
7. По «Сохранить» (любой из трёх способов) — выполняется один и тот же алгоритм из раздела 7; Description, если заполнен, идёт в колонку B вместе с датой/суммой/налогом, если оставлен пустым — колонка B остаётся пустой.

## 9. Экран Driving Details (ручной ввод)

Отдельный экран с тремя полями: Date, Trip (свободный текст, без автодополнения — пользователь сам вписывает маршрут и сам считает километраж), KM (число, десятичные значения разрешены — формула `=SUM(C{r}*$G$1)` их корректно обработает).

После сохранения — запись в первую свободную строку листа Driving Details (2–18) и пересчёт строки Kilometers на листе Truman Homes (раздел 7). Если строки 2–18 закончились — то же предупреждение, что и в разделе 7.

## 10. Timesheet: автозаполнение и редактирование

При создании нового периода (раздел 5) для каждого дня `period.start..period.end` по порядку в строки 8, 9, 10... (Item# 1, 2, 3...):
- Колонка B = дата дня.
- Если день — суббота/воскресенье ИЛИ входит в `stat_holidays` текущего периода (из списка периодов, раздел 5) — колонки C–H остаются пустыми.
- Иначе — заполнить по умолчанию: `C="8am"`, `D="1200-1230"`, `E=""`, `F="430pm"`, `G=8`, `H=8`.
- Дни за пределами периода (Item# больше числа дней в периоде) — колонки B–H остаются пустыми, как в оригинальном шаблоне.
- `H39` = сумма всех H за период, пересчитывается при любом изменении.

Редактирование — по дням: тап на дату → форма со Start/Lunch/Coffee/Finish (time picker'ы, раздел 6.3) → Hours и Total пересчитываются автоматически, не вводятся отдельно → Сохранить. STAT-дни по умолчанию пустые, но остаются полностью редактируемыми — пользователь может вписать часы вручную, если по факту работал.

## 11. Настройки

**Основные:**
- **Язык:** English / Русский, весь интерфейс должен иметь оба набора строк. По умолчанию при первом запуске — English. Это касается только экранов приложения (списки, календарь выбора даты и т.п.) — формат дат и прочего текста, который уходит В Excel-файлы, всегда фиксированный (английский, как в шаблоне, раздел 6), независимо от выбранного языка интерфейса; это две независимые вещи.
- **Имя сотрудника:** First name / Last name, по умолчанию «Truman» / «Homes», редактируется пользователем — используется в B3 (Mileage Report) и C2 (Timesheet) при создании каждого нового периода.
- **Телефон:** аналогично имени — редактируемое поле, по умолчанию пусто — используется в C6 (Timesheet).
- **Хранение предыдущих Excel-файлов:** один переключатель на оба типа файлов сразу — «Никогда не хранить» / «Хранить последний месяц» / «3 месяца» / «6 месяцев» / «последний год». «Никогда не хранить» = в архиве не остаётся ничего, кроме текущего периода. Для остальных вариантов — хранятся периоды, у которых `period.end` попадает в последние N месяцев от сегодняшней даты; всё, что старше этого окна, удаляется. Архив (раздел 14) всегда показывает только то, что укладывается в текущее окно хранения.

  **Смена настройки применяется сразу, а не только вперёд.** Как только пользователь выбирает новое значение — пересчитать окно и немедленно удалить всё, что в него больше не попадает: переключение на «Никогда не хранить» удаляет архив полностью (кроме текущего периода); переключение с более широкого окна на более узкое (например, с 6 месяцев на 3) удаляет всё, что старше нового, более узкого окна, прямо в этот момент, а не при следующей смене периода. При переключении на БОЛЕЕ широкое окно (например, с 3 месяцев на 6) удалять нечего и восстанавливать нечего — то, что уже было удалено раньше, не возвращается; новая настройка просто перестаёт удалять то, что попадёт в архив дальше.

  **Перед применением — предупреждение.** Показывать его нужно, только если у выбора будут реальные последствия прямо сейчас (то есть в архиве действительно есть периоды, которые попадут под удаление при новой настройке) — если удалять нечего (архив пуст или новое окно шире старого), менять настройку сразу, без лишнего диалога. Когда предупреждение нужно — явно назвать масштаб: сколько периодов удалится (или «архив будет полностью очищен» для «Никогда не хранить»), и что это необратимо. Два варианта: подтвердить (применить и удалить) или отменить (настройка остаётся прежней). Диалог всплывает сразу по выбору нового значения в самом переключателе — не по отдельной кнопке «Применить» рядом. Это осознанный выбор: раз диалог и так возникает только тогда, когда действие разрушительное, отдельная кнопка «Применить» добавила бы риск другого рода — выбрали новое значение, забыли применить, недоумеваете, почему ничего не изменилось.

**Дополнительно** (визуально отделить от основных — трогают редко):
- **Управление периодами** — та же форма добавления/правки периода, что описана в разделе 5 («Когда периоды заканчиваются»): даты периода, срок сдачи, отдельный срок для рабочих выходных, STAT-праздники и ставка $/км для этого периода.
- **Ставка $/км:** число, по умолчанию 0.56, редактируется пользователем — используется для расчёта Travel в строке Kilometers (раздел 7). У каждого периода своё значение ставки, зафиксированное на момент его создания (`period.km_rate`, раздел 4) — изменение этой настройки сразу пересчитывает Travel в строке Kilometers ТЕКУЩЕГО периода, если он уже создан, обновляет `period.km_rate` этого периода на новое значение, и записывает то же значение в `G1` на листе Driving Details (раздел 6.2), чтобы формула Excel-файла и расчёт приложения не разошлись. Уже завершённые/архивные периоды не затрагиваются: они хранят ту ставку, что действовала на момент их создания (в том числе в своём собственном `G1`), и не пересчитываются задним числом, даже если позже отредактировать их Driving Details.

## 13. Целостность Excel-файлов — обязательная проверка

Это самое важное требование во всём проекте: при любой записи из приложения все скрытые листы (Truman Dev, Lionsworthe, Taphouse, Metro, Sheet1) и все формулы (I, L, D в Driving Details, строка 28, M30) должны оставаться абсолютно нетронутыми — приложение модифицирует ЗНАЧЕНИЯ только в конкретных ячейках, перечисленных в разделе 6. Единственное исключение — лечение стилей (п. 2 ниже), которое проходит по всем листам, включая скрытые: оно не меняет ни одного значения и ни одной формулы, а лишь возвращает ячейкам то оформление, которое у них и так есть в шаблоне, — то есть работает на сохранение исходного вида, а не против него.

**КАНОНИЧЕСКИЙ ПОРЯДОК ЗАПИСИ.** Все отдельные требования этого раздела складываются в одну последовательность — она обязательна и одинакова для любой записи в любой из двух файлов (новый чек, поездка, день табеля, правка существующей записи, смена ставки). Порядок шагов не переставлять: каждый шаг опирается на результат предыдущего, и мы уже дважды ловили баги именно на неверном порядке (проверка стиля раньше лечения; лечение раньше проверки структуры). Ниже «шаг N» — это шаг конвейера, «п. N» — пункт нумерованного списка требований, который идёт следом; это разные нумерации.

> **Шаг 1.** Прочитать текущий файл периода.
> **Шаг 2.** **Проверка структуры** (п. 1) — ожидаемые заголовки на ожидаемых местах, строка Kilometers находится однозначно (п. 1а). Не прошла → остановиться, показать предупреждение, дальше не идти. Именно здесь, до лечения: лечить стили в файле, который человек перестроил вручную, — значит применить шаблонное оформление к чужой структуре и усугубить расхождение.
> **Шаг 3.** **Резервная копия** текущего файла (п. 5).
> **Шаг 4.** **Лечение стилей** — все ячейки всех листов из карты шаблона (п. 2).
> **Шаг 5.** **Запись значений** в конкретные ячейки (раздел 6), включая высоту строки под длинный текст (п. 12).
> **Шаг 6.** **Проверка целостности** (п. 2): (а)–(в) блокируют сохранение, (г) только предупреждает и логируется.
> **Шаг 7.** Сохранить файл, заменив им прежний, только после успешного шага 6.

1. Перед записью — лёгкая проверка структуры (совпадают ли ожидаемые заголовки в ожидаемых ячейках); если файл был вручную изменён пользователем в стороннем Excel-приложении настолько, что программа не находит нужные колонки — не писать вслепую, показать предупреждение.

   **1а. Строка Kilometers должна находиться ровно один раз.** Она ищется по тексту (ячейка колонки B, начинающаяся на `Kilometers (`) — значит достаточно вручную поправить эту подпись в Excel, чтобы поиск сломался. Оба нештатных исхода — часть проверки структуры и оба останавливают запись, не пытаясь угадать:
   - **0 совпадений** → «строка Kilometers не найдена, файл, вероятно, правился вручную» — запись не выполнять. НЕ создавать строку заново: если пользователь просто переименовал подпись, создание второй строки задвоит километраж в итогах отчёта, и заметить это будет крайне трудно.
   - **больше 1 совпадения** → «найдено несколько строк Kilometers» — запись не выполнять, дальше разбирается пользователь в самом Excel.

   В обоих случаях сообщение должно называть лист и номера строк, чтобы человек мог сразу открыть файл и починить.
2. После каждой значимой операции записи — тест, который открывает результат и проверяет: (а) 5 скрытых листов остаются скрытыми, их содержимое не изменилось; (б) ячейки-формулы по-прежнему содержат формулы, а не числа; (в) файл открывается без ошибок; (г) у каждой записанной ячейки border, font (имя+размер) и number_format совпадают с тем, что было в этой же ячейке в чистом шаблоне до записи. Пункты (а)–(в) фатальны и блокируют сохранение — это реальное повреждение данных. Пункт (г) — НЕ блокирует сохранение, а логируется как предупреждение (обоснование и обязательный порядок операций — ниже). На практике: перед первой записью в файл периода сохранить словарь «координата ячейки → её стиль» по всем ячейкам шаблона, и после каждой записи сверять актуальный стиль записанных ячеек с этим словарём.

   **Почему стиль — предупреждение, а не блокировка, и как при этом не оставить старые файлы визуально повреждёнными навсегда:** перед КАЖДОЙ записью (до проверки (г), не после) — проактивно переприменять стиль шаблона ко ВСЕМ ячейкам ВСЕХ листов файла, включая скрытые (не только к той, что редактируется в этот раз, и не только к управляемым — см. раздел 0, п. 1: узкой области оказалось недостаточно, часть повреждений приходит не от наших записей, а от пересохранения книги пакетом `excel`), используя тот же словарь «координата → стиль», снятый с шаблона. Это самостоятельно залечивает повреждения, оставшиеся от использования более ранних версий приложения, в ходе обычного использования — без отдельного шага миграции. Порядок обязателен: сначала лечение, потом проверка (г). Если проверка идёт первой — она заблокирует сохранение именно в уже повреждённых файлах ещё до того, как лечение успеет сработать, и вся функция станет бесполезной ровно для тех файлов, которые и нужно вылечить. При правильном порядке проверка (г) — это просто подтверждение, что лечение сработало (в норме всегда проходит), поэтому её безопасно понизить до предупреждения; блокирующей она не нужна, а полезна как раз для единственного известного случая, когда лечение принципиально невозможно: текстовое значение в ячейке с числовым/временны́м форматом (например, «8am» в ячейке, форматированной как `h:mm`) — Excel всё равно игнорирует number_format у текстовых значений, визуально это ничего не меняет, но формально стиль «не совпадёт», и это ожидаемо, не повод блокировать сохранение.
3. Библиотека `excel` не хранит закешированные значения формул — при открытии результата в Excel/Google Sheets/LibreOffice они пересчитаются автоматически (так уже работает с этими файлами и сегодня) — отдельно внутри приложения ничего пересчитывать не нужно.

   **Осознанное следствие лечения стилей, о котором надо знать:** раз лечение проходит по всем ячейкам всех листов, любое оформление, которое пользователь задал вручную в самом Excel (покрасил ячейку, сменил шрифт, поменял формат числа), при следующей записи из приложения вернётся к шаблонному. ЗНАЧЕНИЯ, введённые вручную (Travel, Phone, Meals, Showhome и любые другие), при этом не трогаются — только оформление. Это принято сознательно: пользователь работает в Excel со значениями, а не с форматированием, поэтому цена такого поведения близка к нулю, а альтернатива (лечить ячейку только если её стиль похож на дефолт Excel, то есть на потерю) добавила бы условную логику в самый ответственный участок кода ради сценария, которого, скорее всего, не будет. Если окажется, что пользователь действительно форматирует файл руками — вернуться к этому решению и реализовать вариант с проверкой на «похоже на потерю».
4. Приоритет в разработке: до того как строить экраны — написать тестовый скрипт, который берёт именно `Truman_Homes_Mileage_Report_TEMPLATE.xlsx` и `Truman_Homes_Timesheet_TEMPLATE.xlsx`, прогоняет через них весь набор операций записи (несколько чеков подряд, несколько записей Driving Details, несколько дней Timesheet) средствами пакета `excel`, и проверяет пункты 1-2. Эти файлы уже проверены мной через openpyxl и пересчёт в LibreOffice (0 ошибок формул) — но это другой инструмент, не тот, которым будет писать сама программа на Dart, поэтому фиделити именно через `excel` нужно подтвердить отдельно, до того как строить остальное приложение поверх этого слоя.
5. Перед каждой записью сохранять резервную копию текущего файла периода (например, в приватную папку приложения) и подтверждать успешность новой записи, прежде чем заменять ею старый файл. Если запись обрывается на середине (приложение закрыли, села батарея) — при следующем запуске программа должна уметь распознать неполный/битый файл и предложить восстановить из резервной копии, а не молча продолжать поверх повреждённого состояния. Когда срок хранения (раздел 11) удаляет файлы периода — удалять заодно и его резервную копию, если она осталась, а не только «основной» файл: иначе копии старых, уже недоступных пользователю периодов будут молча копиться в хранилище телефона бессрочно.
6. Целостность объединённых ячеек: после серии записей сверять, что диапазоны merge (I:J и L:M на каждой строке 8–27 Truman Homes) точно совпадают с шаблоном — библиотека, записывая соседнюю ячейку (A/B/D/K), теоретически может разъединить merge или перепутать, в какую половину пишет.
7. Точность округления `round(N × rate, 2)` (ставка — по правилу старшинства раздела 6.2): не полагаться на то, что "выглядит верно" — тест берёт конкретный набор пар (км, ставка) → ожидаемый результат (включая случаи, где особенности чисел с плавающей точкой могут дать на цент не то, например 0.1+0.2), и сверяет код в код, а не на глаз.
8. Формулы в I/L/D (Driving Details) сверять по точному тексту, не только по типу "это формула": тест из пункта 2(б) ловит замену формулы на число, но не заметит, если библиотека исказит саму строку формулы (потеряется член, сместится порядок ссылок на ячейки). Сравнивать строку формулы посимвольно с ожидаемой.
9. Переход на летнее/зимнее время в Timesheet: период `2026-10-24 – 2026-11-08` в `payroll_periods_seed.json` реально захватывает дату перевода часов в Канаде (1 ноября 2026 — воскресенье). Тест на этом периоде должен подтвердить, что Hours для соседних дней не съезжает на час — то есть что часы считаются по написанному тексту времени (`8am`–`430pm` минус обед), а не наивной разницей datetime, чувствительной к переводу времени.
10. Путь "период добавлен вручную через форму (раздел 5) → ставка km_rate из формы": добавить тестовый период через форму с km_rate, отличным от 0.56, добавить в него поездку и убедиться, что Travel считается именно по этой ставке, а не по забытому дефолту 0.56.
11. Синхронизация `G1` на листе Driving Details (раздел 6.2): после создания нового периода и после смены ставки в Настройках — открыть файл и убедиться, что `G1` действительно содержит правильное значение `period.km_rate`, а не забытый дефолт. Проще всего проверяется через пересчёт файла (например, той же связкой openpyxl+LibreOffice, что использовалась при подготовке шаблонов) — «Total $» на Driving Details после пересчёта должен совпасть с Travel, посчитанным приложением. Отдельно — тест на согласованность трёх копий ставки (раздел 6.2, «Приоритет источников»): после любой смены ставки `G1` в файле текущего периода и `period.km_rate` в локальном списке должны быть равны; расхождение = баг синхронизации, поймать его тестом, а не через месяц в отчёте.
12. Высота строки при длинном тексте: и Description на Truman Homes (колонка B, строки 8–27), и Trip на Driving Details (колонка B, строки 2–18) — свободный текст переменной длины. Обе колонки в актуальном шаблоне уже настроены на перенос текста (wrap text) с достаточной для нескольких строк высотой — но это стартовая точка, не гарантия на будущее. Если запись длинного текста (в том числе при редактировании — заменили короткое на длинное, раздел 14) не сопровождается соответствующей высотой строки, лишние строки перенесённого текста визуально обрежутся, хотя сами данные в ячейке останутся целыми и корректными — тест должен ловить именно это визуальное обрезание, не только целостность данных. При каждой записи в любую из этих двух колонок — либо использовать автоподбор высоты строки, если библиотека `excel` его поддерживает (предпочтительно), либо оценивать нужное число строк переноса по длине текста и ширине колонки и выставлять высоту вручную, не меньше нужной. Остальных колонок (Date/Subtotal/GST/KM) не касается — они всегда короткие и фиксированного формата.
13. Стиль ячеек ВНЕ управляемых (раздел 0, п. 1): тест, который проходит по ВСЕМ ячейкам ВСЕХ листов сохранённого файла (включая 5 скрытых) и сверяет border/font(имя+размер+жирность)/number_format с шаблоном. Это шире, чем проверка 2(г), которая смотрит только на записанные ячейки, и ловит именно тот класс потерь, который приходит не от наших записей, а от пересохранения книги пакетом `excel`. Ожидаемый результат после расширения самолечения — ноль расхождений (единственное допустимое исключение — `number_format` у текстовых значений во time-ячейках Timesheet, см. п. 2). Полезно зафиксировать в тесте и числовой ориентир: на реальном файле периода Aug 9–23 до расширения расхождений было 176, после должно стать 0.

## 14. Решения, подтверждённые пользователем отдельно от основного ТЗ

- **Просмотр старых периодов.** Прошлые периоды (пока не истёк срок хранения) можно открыть и редактировать теми же экранами, что и текущий период, через простой список/переключатель периодов.
- **Просмотр и редактирование уже сохранённых чеков и поездок.** У выбранного периода (текущего или архивного, раздел 5) — список уже внесённых чеков (строки 8–27 листа Truman Homes, кроме строки Kilometers — она не показывается в этом списке как обычный чек, ей управляет только раздел 7) и отдельно список поездок (строки 2–18 листа Driving Details). Точное место в навигации, откуда открывается этот список (кнопка/вкладка на экране периода и т.п.), — на усмотрение реализации, важно чтобы он был легко доступен.

  **Список всегда читается заново из текущего Excel-файла в момент открытия экрана**, а не из отдельно поддерживаемой копии/базы данных внутри приложения. Причина — то же самое допущение, что уже есть в разделе 13, п. 1: файл мог быть изменён вручную в стороннем Excel-приложении, а значит любая отдельно хранимая копия списка рискует показать пользователю устаревшие данные вместо того, что реально лежит в файле.

  Тап по элементу списка открывает: для чека — тот же экран, что и при добавлении (раздел 8), для поездки — тот же экран, что и ручной ввод (раздел 9); в обоих случаях — предзаполненный текущими значениями этой строки, все поля сразу редактируемые (как в режиме «Ввести вручную» — без кнопки «Редактировать», сразу «Сохранить»). Проверка «GST ≈ 5% от Subtotal» (раздел 8) действует и здесь.

  Технически новая логика сдвига строк не нужна: правка идёт в ту же строку, где чек/поездка уже находится — без обращения к алгоритму из раздела 7 (он нужен только при ДОБАВЛЕНИИ нового чека/поездки, не при правке существующего). Исключение — если поменяли KM у поездки, общая сумма километров меняется, значит нужно, как и при добавлении, пересчитать и Description, и Travel в строке Kilometers («Алгоритм при изменении Driving Details», раздел 7) — эта часть логики уже существует и просто переиспользуется, а не пишется заново.

  Не плодить дублирующий код: используй тот же UI-компонент экрана подтверждения (раздел 8) и ту же функцию записи значения в ячейку с сохранением стиля (раздел 13), что уже написаны для добавления — редактирование это тот же код в режиме «дана существующая строка», а не отдельный написанный с нуля экран.

  Удаления НЕТ — сознательное решение, только просмотр и правка значений на месте.
- **Старые файлы, которые пользователь вёл вручную до этого приложения, никак не импортируются.** Приложение при первом запуске просто определяет текущий период на сегодняшнюю дату (раздел 5) и начинает с него — прошлые периоды из истории пользователя ему не известны и не нужны.

## 15. Сборка и тестирование

- Сборка и тестирование — через Android Studio (`flutter run` на эмулятор или физическое устройство). Аккаунт разработчика Google/Apple для этого не нужен — такие аккаунты нужны только для публикации в магазины, чего пока не планируется (сейчас — публикация исходников на GitHub).
- **На реальном телефоне пользователя уже стоит рабочая версия с реальными данными** (текущий период, возможно архив). Обновление — переустановка ПОВЕРХ существующего приложения (обычное поведение `flutter run`/Android Studio при том же package name), а не удаление и установка заново: удаление приложения перед переустановкой сотрёт всё локальное хранилище, из-за чего раздел 0 (сравнение с уже работающей версией) потеряет смысл. Если для тестирования нужно чистое состояние — использовать отдельный эмулятор/тестовое устройство, не тот телефон, где уже есть реальные данные пользователя.
- iOS не реализовывать в этой итерации, но не принимать архитектурных решений, которые сделают будущий iOS-билд невозможным (не завязываться на Android-специфичные API там, где есть кроссплатформенный аналог в Flutter).
